TP6 - Prefect + GitHub Actions

Automatiser les workflows MLOps

Jusqu'ici, quelqu'un devait taper dvc repro, lire le F1 et prevenir l'equipe. Ici, le pipeline devient un workflow qui tourne seul chaque lundi, s'arrete seul si le modele est mauvais, et chaque git push est verifie automatiquement.

01Le fil : d'ou on vient, ou on va2 min

Chaque TP resout le probleme laisse par le precedent. Si tu retiens cette chaine, tu retiens le cours.

Probleme herite
TP3-TP5 : tout marche, mais tout est manuel. Si personne ne lance dvc repro lundi matin, rien ne se passe ; si personne ne lit le F1, un mauvais modele passe.
→
Ce que ce TP apporte
Prefect transforme le pipeline en workflow de 4 taches observables, planifie (cron), avec reessais et arret sur la regle de qualite. GitHub Actions rejoue le pipeline a chaque git push et passe au rouge si le F1 tombe.
→
Probleme laisse au suivant
On sait lancer et verifier. Reste a emballer le service (Docker), le deployer a grande echelle (Kubernetes) et surveiller la derive des donnees en production.
H

L'horloge et le controle qualite

Prefect, c'est le chef d'atelier avec une horloge : chaque lundi a 6 h il lance la chaine (taches), regarde chaque poste, recommence si une machine cale (reessais), et arrete tout si la piece est hors norme (valider). GitHub Actions, c'est le controle qualite a l'entree de l'usine : chaque nouvelle piece de code est testee avant d'entrer. L'un fait tourner la production, l'autre protege l'entree.

08Comprendre vraiment3 min

Feynman : connaitre le nom n'est pas comprendre. Pour chaque idee : pourquoi c'est vrai, a quoi ca se rattache, et ce qui casserait si c'etait faux.

Pourquoi 2 reessais sur rejouer_pipeline mais 0 sur valider ?

Pourquoi c'est vrai
rejouer_pipeline peut echouer pour une raison passagere (fichier verrouille, disque, reseau) ; valider echoue pour une raison deterministe (le F1 est bas).
Lien avec ce que tu sais
On recompose un numero occupe ; on ne recompose pas un numero qui n'existe pas.
Et si c'etait faux ?
Avec des reessais sur valider, on attendrait 20 s de plus pour le meme refus, et l'alerte arriverait en retard.

Pourquoi le run reste 'Late' quand serve est arrete ?

Pourquoi c'est vrai
Le serveur garde le plan, mais n'execute rien lui-meme : il faut un processus (serve ou worker) qui vient chercher le travail.
Lien avec ce que tu sais
Le planning du restaurant existe, mais si aucun cuisinier n'est la, aucune commande ne sort.
Et si c'etait faux ?
Si le serveur executait tout, on ne pourrait pas repartir le travail sur plusieurs machines (work pools).

Pourquoi la CI regenere les donnees au lieu de dvc pull ?

Pourquoi c'est vrai
Le stockage DVC est un dossier de ton poste : la machine GitHub n'y a pas acces. Les graines fixes rendent la regeneration exacte (F1 0.8423).
Lien avec ce que tu sais
C'est le TP1 et le TP3 qui paient : graines fixes + pipeline declaratif = rejouable n'importe ou.
Et si c'etait faux ?
Sans graines fixes, la CI obtiendrait un autre F1 et la verification ne voudrait rien dire.

10Quiz : retrouve de memoire2 min

Reponds dans ta tete avant d'ouvrir. Chercher la reponse en memoire grave mieux que relire.

Orchestrateur vs CI en une phrase ?
La CI verifie le CODE a chaque modification ; l'orchestrateur execute et surveille les TRAITEMENTS recurrents.
Que veut dire cron 0 6 * * 1 ?
Minute 0, heure 6, tous les jours du mois, tous les mois, le lundi (UTC par defaut).
serve vs work pool + worker ?
serve : un seul processus deploie et execute. Work pool : le serveur garde les deploiements, des workers separes executent.
Pourquoi git revert et pas git reset ?
revert ajoute un commit qui annule, sans reecrire l'historique deja pousse et partage.
Un autre declencheur qu'une date ?
L'arrivee de nouvelles donnees (md5 du ticket .dvc qui change) ou une derive detectee en production.
